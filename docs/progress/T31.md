# T31 — ble_service: sync status and recent records

**Date:** 2026-10-27 · **Verification:** host/CI + firmware compile · **Result:** done
**Board:** real phone transfer pacing, cancel latency and MTU negotiation are
deferred to T37; the host byte streams and the image guard are the gate now.

## What landed

- `firmware/components/ble_service/include/ble_sync.h`, `ble_sync.c` — pure C11:
  - exact 10-byte `sync_ctrl` parser (`ver`, `cmd`, `direction`,
    `cursor_seq`, reserved, `max_records`); 0 → 32, >64 → 64;
  - `ble_sync_plan()` busy policy: status and cancel always allowed, a read is
    ignored while a record transfer is in flight;
  - logical builder: START (20 B) / RECORDS (`count × 18` B) / END (13 B),
    snapshotting generation/min/max once;
  - forward window (`seq > cursor`, clamp to `min_seq`, `next_seq = last+1`) and
    backward window (highest records below cursor, emitted ascending,
    `next_seq = first`);
  - empty log → `status = empty`, `min = max = 0xFFFFFFFF`, `count = 0`;
  - record read failure truncates before the hole and sets `status = error`;
  - framer: 4-byte header, `len = min(240, MTU-3-4)`, START on the first frame,
    END/ERROR on the last, `frame_seq` restarts at 0 per response.
- `firmware/components/ble_service/ble_service.c`:
  - ring adapter uses `sample_log_get_info()` / `sample_log_read_seq()` +
    `sample_log_record_encode()`;
  - `write_sync_ctrl()`: routes status (sent immediately; 33 B), cancel, and a
    read (ignored without a `sync_data` subscription or while busy);
  - a 15 ms one-shot `esp_timer` builds the stream on the first tick and sends
    one notification per tick, so status/cancel can interleave; a mutex keeps
    each status response contiguous;
  - `sync_active` is set when a read starts and cleared on end/cancel/
    unsubscribe/disconnect/reset/stop;
  - `sync_data` CCCD tracked separately from `live`/`result`.
- `firmware/test/test_ble_sync.c` + `ble-sync` CTest (21 suites total): a
  client-style reassembler covers MTU 23 (16 B frames, 20 B START spanning two
  frames, records split across boundaries), MTU 247 (3-frame 609 B batch),
  a 64-record batch (75 frames at MTU 23, 5 at MTU 247), dropped `frame_seq`,
  status/empty, backward ascending last-15-min, backward/forward cursor edges,
  error truncation and small-buffer refusal.
- Docs: design 04 §4.5 implementation note, design 05 §5.7/5.8 implementation
  rules, ADR 0038.

## Deviations / decisions

- No new FreeRTOS task: the `tasks.h` budget stays at 6 rows / 22 KB. Sync uses
  an `esp_timer` pump (one frame per 15 ms) instead of a second BLE writer.
- `frame_seq` restarts at 0 for every response. A status response interleaved
  with a read therefore starts with a START frame; the client must reset its
  reassembly on START rather than assuming one contiguous sequence per link.
- Forward gap reporting is deferred to T39; a forward cursor below `min_seq`
  simply clamps to `min_seq` with `status = ok`.
- A failed record read ends the batch with `status = error` and a truncated
  `count`; the START header is re-encoded with the emitted count.
- A malformed `sync_ctrl` body is ignored. A wrong length is rejected by ATT.
- `bridge_state_set_sync_active()` is idempotent; disconnect already called it
  in T30, and `sync_cancel()` now also clears it.

## Gotchas for later tasks

- **Subscribe first.** Without `sync_data` CCCD notification, a read is ignored.
  The app reads `sync_ctrl` only after decrypting the link and subscribing.
- **Never assume one record per notification.** Feed frames into a byte stream,
  verify `frame_seq` contiguity, and reset on the START flag.
- **Status during a transfer** may interleave with record frames; its response
  begins with its own START. Do not treat an interleaved START as corruption.
- **The static stream buffer is 1,185 B** (`BLE_SYNC_STREAM_MAX`). Raising the
  64-record cap means chunking the builder, not enlarging the buffer.
- **`have_seq`** from T28 is irrelevant here: empty is `extent.count == 0`, and
  the wire sentinels are `SX4_SEQ_NONE` for min/max.
- **NimBLE callback context:** the write callback only parses/arms the timer;
  `sample_log_*` flash reads happen in the esp_timer task. Do not move them back
  into the GATT callback.
- **Cancel** has no response (design 04 §4.5). The app infers it from the absent
  END and sends the next request.

  re-requests rather than storing a partial stream.
