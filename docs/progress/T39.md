# T39 — ble_service: full sync cursor, gap, and generation

**Date:** 2026-10-27 · **Verification:** host/CI + firmware compile · **Result:** done
**Board:** no board run in this task. A real phone transfer is still useful in
T41/T55 for app-side cursor persistence; the wire bytes are the host gate now.

## What landed

- `firmware/components/ble_service/ble_sync.c`:
  - forward `seq > cursor`, lowest first, `next_seq = last_seq + 1`;
  - forward `gap` iff `min_seq > 1 && cursor_seq < min_seq - 1`, restarting at
    `min_seq`; `min_seq - 1` is never formed when `min_seq` is 0, so `seq = 0`
    remains a real record;
  - backward highest records below the cursor, emitted ascending,
    `next_seq = first_seq`; `gap` iff `cursor_seq > max_seq + 1` (64-bit add),
    restarting at `max_seq + 1`;
  - drained direction: `count = 0`, `start_seq = next_seq = cursor_seq`,
    `status = ok`, including a backward cursor of 0;
  - empty whole log: `status = empty`, `count = 0`,
    `min_seq = max_seq = 0xFFFFFFFF`;
  - gap responses still carry records (the app learns the missed range and gets
    the nearest live edge);
  - `next_seq` advances only on `ok`/`gap`; on `error` it stays at the request
    cursor so the app re-requests the truncated batch;
  - one extent snapshot per response; `generation` and min/max in START and
    min/max in END come from that snapshot, so mid-transfer writes appear only in
    the next request;
  - `max_records` normalised to 1..64 (0 → 32) in both the parser and the
    builder;
  - `cmd` 0/1/2 and the busy policy were already present and are unchanged:
    status/cancel allowed while busy, other reads ignored.
- `firmware/test/test_ble_sync.c` adds host coverage for:
  - both gap edges and the `min_seq = 0/1` non-gap cases;
  - the last 24-bit sequence and `max_seq + 1` without overflow;
  - a generation change with a record written during the build (old
    generation/extent in this response, new one in the next);
  - `frame_seq` wrapping through 255 → 0 mid-response;
  - a disconnect after two frames, then a clean re-request of the same cursor;
  - a 90,000-record ring walked backward in 64-record batches: the newest 86,400
    (30 days at 30 s) plus the rest of the ring down to `seq 0`, then a
    zero-record forward terminator;
  - direct-builder `max_records` normalisation.
- Docs: 04 §4.5 implementation note, 05 §5.7/5.8 implementation rules,
  ADR 0044; ADR 0038 now points to 0044 for the T39 extension.

## Decisions / deviations

- **Generation is not in END.** The fixed wire contract (04 §4.5, 05 §5.8,
  `protocol/ble.yaml`) gives END 13 B: status, next_seq, min_seq, max_seq. The
  acceptance wording asks for generation in START and END, but adding a field
  would break the app codec and the "fixed" format. The extent (including
  generation) is snapshotted once at START; END repeats the same min/max and the
  START generation is the epoch for the response. Recorded in ADR 0044.
- Gap stays `status = gap` on both START and END, and still emits the records
  from the live edge. The app can store those records and mark the skipped range.
- A status (`cmd = 0`) response always reports `status = ok` for a non-empty log
  and `empty` for an empty one; it never reports `gap` because it has no cursor
  direction semantics.
- The 30-day check is a host volume loop, not a phone run. It exercises every
  batch and the terminator; app cursor persistence is T41.

## Gotchas for later tasks

- **Seq is 24-bit in the record** (`sx4_seq24_*`) while sync fields and
  `SX4_SEQ_NONE` are u32. Tests cannot encode `0xFFFFFFFE` as a record; the last
  valid record sequence is `0xFFFFFF`. `SX4_SEQ_NONE` (0xFFFFFFFF) only means
  empty/extent sentinel.
- Forward `gap` requires `min_seq > 1`. Do not "simplify" it to
  `cursor < min_seq - 1`: with `min_seq = 0` that underflows to 0xFFFFFFFF.
- Backward `max_seq + 1` must stay in 64 bits; `0xFFFFFFFF + 1` is otherwise a
  false wrap.
- `count = 0` is the normal drained terminator for **both** directions;
  `next_seq = 0` is a valid backward cursor, not a stop sentinel. Stop when
  `count == 0`, not when `next_seq == 0`.
- On `error`, `next_seq` stays at the request cursor by design; re-request the
  batch rather than advancing past the hole.
- The START/END min/max are a snapshot. If the app sees a different generation
  on the next START while a transfer was in flight, start a new local segment.
- The static stream buffer is still `BLE_SYNC_STREAM_MAX` (1,185 B). 64 records
  is the ceiling; do not raise it without a chunked builder.
- `ble_service.c` only changed in T31; T39 is entirely in the pure builder and
  its host tests. Live notifications remain on the separate `ble_tx` queue.

## Follow-ups

- **T41:** app-side cursor persistence, two-phase sync and resume: treat
  `status = gap` as a permanent missed range, store from `start_seq`, stop a
  direction only on `count = 0`, reset cursors on a generation change, and
  re-request after an `error`/`frame_seq` hole. The host test `check_full_ring_backfill`
  is the device-side model for that loop.
- **T37/T55 (board):** run a real MTU 23 and MTU 247 transfer, a cancel while
  busy, a disconnect after a few frames, and a generated-gap run; confirm
  `live` notifications keep flowing during a long sync. Not needed for host
  acceptance.
- **T44 (retention/clear):** when a clear changes `generation`, verify the next
  START reports the new value and an old cursor returns `gap`, not resurrected
  records.
