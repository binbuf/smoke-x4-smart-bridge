  `sample_log_get_info`, `sample_log_ready`, `sample_log_storage_state`,

## Facts for later tasks

- Boot order already calls `sample_log_init` (design 03 step 5) before the radio.
  `bridge_config_init` must have succeeded; otherwise the log is `READ_ONLY`
  unless a sector header can restore the generation.
- `sample_log_append` returns `ESP_OK`, `ESP_FAIL` (flash failure → READ_ONLY,
  no sequence assigned), `ESP_INVALID_ARG` (bad record), or
  `ESP_ERR_INVALID_STATE` (not mounted/already failed). Do not retry a failed
  append; reboot recovery is the retry path.
- `sample_log_get_info` is no-I/O and gives `generation`, `min_seq`, `max_seq`,
  `next_seq`, `count`, `live_sectors`, `sector_count`.
- `sample_log_storage_ok()` is false only for `READ_ONLY`; `NEAR_FULL` still
  records. Map it to `stats.flags.storage_ok` and `live.flags.storage_ok`.
- One writer is assumed; there is no lock in the ring or adapter. Keep all
  appends on the log-writer task (T21).
- Pending clear: boot erases every non-blank sector, skips blank ones (resume),
  then calls `bridge_config_finish_log_clear`. A first full clear can take tens
  of seconds; show progress in T48/T55 and do not assume boot is fast.
- NVS generation wins. If NVS is lost, the newest valid sector header is adopted
  and persisted with `bridge_config_set_generation`. A blank log calls
  `bridge_config_regenerate_generation` and lazy-formats.
- Header-repair read-back failure fails the mount (READ_ONLY); no implicit
  reclaim. This answers T18's open question.
- Boot recovery = **899 ms** on the bench board over the full 6,160,384-byte
  partition (blank; scan reads every sector once). Under ~2 s, so no
  newest-sector-only fast path. Re-measure if the partition or scan changes.
- Adapter read cache: 32-byte reads at sector base bypass it; 4 KB fills serve
  the 18-byte record walk. Writes/erases invalidate.
