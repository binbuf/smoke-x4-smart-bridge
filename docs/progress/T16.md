# T16 — sx_radio: pairing state machine and TX guard

**Date:** 2026-10-26 · **Verification:** host/CI + firmware compile · **Result:** done
**Board:** real-X4 pairing deferred to T37 (unattended run; host FSM/TX-guard is the gate)

## What landed

- `firmware/components/sx_radio/include/sx_radio_pair.h` — pure-C pairing API:
  states `UNPAIRED / SYNC_RECEIVED / PAIRED (CONFIRMED) / LOST`, the
  `{device_id, frequency_hz, num_probes}` record, tunable/loadable/clearable
  callback seams, counters, and the 915/920 scan and 600 s timeout constants.
- `firmware/components/sx_radio/sx_radio_pair.c` — the FSM:
  - unpaired scan alternates 915 ↔ 920 MHz every 3.3 s;
  - sync beacon: parse, 902–928 MHz check, format `<id>,SUCCESS,`, retune,
    send once, then `SYNC_RECEIVED`; further beacons ignored;
  - first matching state packet learns `num_probes` from its comma count
    (26 → 4, 16 → 2), saves through the callback, enters `PAIRED`;
  - a failed save stays in `SYNC_RECEIVED` and retries on the next packet;
  - 10 min with no valid state packet → `LOST` (radio stays tuned, no scan,
    record kept); next valid state packet → `PAIRED`;
  - unpair clears through the callback, returns to `UNPAIRED` and restarts the
    scan; a failed clear leaves pairing intact;
  - exactly one call to `s_pair.io.send_ack(...)`, in the sync handler.
- `firmware/components/sx_radio/sx_radio.c` — adapters:
  - load/save/clear use `bridge_config` (only NVS owner);
  - `pair_tune` uses `sx_radio_set_frequency()` (902–928 MHz check);
  - `pair_send_ack` holds the **only** `LoRaSend()` call in the product;
  - `sx_radio_init()` loads pairing (or starts on 915 MHz) before
    `LoRaBegin()`, so a reboot tunes the persisted frequency;
  - the RX task feeds every raw frame to `sx4_radio_pair_on_packet()` and
    calls `sx4_radio_pair_tick()`; the raw frame is still published to the
    parser seam for T21.
- `firmware/test/test_sx_radio_pair.c` + `sx-radio-pair` CTest: scan timing,
  pair → persist → reboot reload, foreign first state, out-of-band 900/930 MHz
  (never tunes/TXs), malformed beacons, ACK failure rollback, save-failure
  retry, X2 probe learning, unpair/re-pair, LOST/recovery, runtime TX-guard,
  and a source scan asserting one `LoRaSend(` and one `send_ack(` call site.
- Docs: design 02 §2.7, design 03 §3.5.3/§3.6; ADR 0024.
- Firmware build: `sx4_bridge.bin` 0x3aa70 bytes, image guard ok.

## Gotchas for later tasks

- `sx_radio.c` needs `esp_timer` in `PRIV_REQUIRES`; adding `esp_timer.h`
  without it fails the IDF build.
- The pairing FSM already parses state frames to learn `num_probes`. T21 must
  keep consuming the raw seam; do **not** call `sx4_radio_pair_on_packet()`
  again from the sample pipe or a second ACK path can appear.
- Sync beacons are still published to the seam. T21 must skip 6-comma sync and
  2-comma ACK frames (as T14 already noted).
- Pairing state is written by the `radio_rx` task only. A later BLE
  `unpair_smoke_x` handler (M4) must serialize with that task or add a lock;
  calling `sx4_radio_pair_unpair()` from another task races the radio task.
- `bridge_config_set_pairing()` validates ID/frequency/probes; `paired_at` is
  written as 0 (unknown) because the radio task has no wall clock. T20 may
  update it later if a paired-at timestamp is needed.
- A paired reboot starts `PAIRED` with `last_valid = now`; the 10-minute LOST
  countdown starts from boot, so the first post-boot state packet refreshes it.
- Out-of-band beacons are rejected before format/tune/TX. A failed ACK restores
  the previous tuning and leaves the FSM `UNPAIRED`; the next beacon retries.
- `SX4_RADIO_DEFAULT_FREQUENCY_HZ` remains 915 MHz for the unconfigured case,
  but `sx_radio_init()` now lets the FSM/`bridge_config` choose the frequency
  first.
