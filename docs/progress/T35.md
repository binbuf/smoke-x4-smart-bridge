  - The fixed procedure: connect → read `info` → MTU 247 → bond when not
    secured → subscribe `live`/`result`/`sync_data` → read `live` →
    `control(set_time)` → sync. `completeFirstConnect(device)` starts after the
    setup bond; `connectAndSecure(device)` runs the full order for a fresh link.
  - Control queue: non-reused 0–255 `op_id`, 3 s timeout, match on op + op_id,
    branch on `result.status`; write rejection maps to `bondRequired` and takes
    the bond path once.
  - `set_time` with phone UTC ms + `tz_offset_min`; first connect always sets;
    reconnect compares wall-clock vs monotonic elapsed since the last set and
    re-sends when `clock_valid` is false or the difference exceeds 2 s.
  - Reconnect backoff 1/2/4/8/15/30 s, cancellable wait for pull-to-refresh and
    app resume, `FAILED` after six attempts.
  - Health watchdog 110 s → read `live`; fresh → LIVE, quiet → STALE, failure →
    RECONNECTING. Any GATT disconnect → RECONNECTING.
  - Recent sync is backward over the **last 15 minutes**; reconnect syncs

    `BridgeSyncSink` (no-op in V0) and the cursor to `onLocalMaxSeq`.

## Deviations / decisions

- The bridge clock is not readable in V0 (stats is out of scope). Reconnect
  compares the phone's wall clock with monotonic elapsed time since the last
  successful `set_time`; `live.clock_valid` forces a reset after a bridge power
  loss. See ADR 0042.
- The procedure bonds proactively when `bondState` is not bonded, rather than
  deliberately reading `live` to provoke ATT `0x0F`. Any security failure on a
  read/write still takes the same one-shot bond path and never loops.
- Recent sync advances the local cursor to the bridge max even when older
  records fall outside 15 minutes. That is deliberate V0 skip semantics; the
  background/older load belongs to T39–T41.
- A reconnect-time re-pair has no approved passkey surface yet; `bond()` is
  called with the OS dialog. Setup still owns the "look at the Bridge screen"
  instruction before the first bond.

## Post-T35 real-device connectivity fix (2026-10-27)

The first real-phone/real-board attempt exposed discovery and failure-path
problems that the fake could not show:

- **App scan dropped later scan-response data.** `FlutterBluePlusBleClient`
  remembered each address once and ignored every later report. Android can emit
  the primary advertisement before the scan response, so a bridge could appear
  with no name/manufacturer block and never be updated. The client now merges
  reports and re-emits only when name, service UUIDs or manufacturer data change.
- **Android status 133 on the first connect.** The real client now waits after
  stopping the scan and retries a failed connection once, sequentially.
- **A transport error looked like "No Bridge found".** `_prepareLink()` let a
  raw `BleException` escape, so setup fell through to the scan/no-results page.
  It now maps to a named `BridgeLinkException`, and setup has a dedicated
  `Couldn't connect to the Bridge` state with `Try again` (no rescan) and
  `Find another Bridge`.
- **Firmware long reads returned GATT_INVALID_OFFSET.** The first attempt at a
  Read Blob fix made `read_value()` append only `value[offset..]`. NimBLE's
  `ble_gatts_val_access()` computes `len(returned) - offset`, so on the second
  Read Blob that became negative and Android saw `GATT_INVALID_OFFSET (0x07)`
  on `info` (captured live with adb). The callback must append the **complete**
  value; NimBLE owns both the MTU-1 truncation for offset 0 and the
  `value[offset..]` copy for later offsets. It now does exactly that.
- **Local-name suffix used the wrong MAC bytes.** NimBLE stores the identity
  address LSB-first, while contract names use printed MAC order. A board with
  MAC `AC:A7:04:38:82:76` advertised `SmokeX4-A7AC`; it now advertises
  `SmokeX4-8276`, and `info.device_id` matches.
- **Advertising identity/watchdog.** `on_sync()` now calls
  `ble_hs_util_ensure_addr(0)` and prefers the public identity address (stable
  `SmokeX4-XXXX` name and `info.device_id`), and housekeeping restarts
  advertising whenever the host is synced, idle and not advertising.
- **The firmware never received the passkey event (root cause on hardware).**
  `ble_gap_adv_start()` was passed `NULL` as its GAP callback and the service
  relied on `ble_gap_event_listener_register()`. NimBLE routes
  `BLE_GAP_EVENT_PASSKEY_ACTION` and `PARING_COMPLETE` only to the connection /
  advertising callback, so the bridge never generated, displayed or injected a
  passkey. The phone waited 30 s, logged `SMP_RSP_TIMEOUT`, then wrongly stored
  a zero-key bond; every later connect tried that bond, got
  `HCI_ERR_KEY_MISSING`, and started an autonomous repair that timed out again.
  Advertising now passes `ble_service_gap_event` directly (and no duplicate
  global listener), and the GAP service name is set to the full
  `SmokeX4-XXXX` instead of just `SmokeX4-`.
- **Passkey could be invisible.** Pairing often starts after the 60 s display
  timeout. `ui_set_passkey()` marked the overlay dirty but did not wake the
  panel, so the user could get an Android pairing prompt while the OLED stayed
  dark. Showing a six-digit code now wakes the display (and restarts its
  timeout); clearing it does not.
- **Discovery indicator.** The Probes page status strip shows a blinking `BT`
  while the bridge is advertising and no phone is connected. The panel still
  sleeps normally; the indicator is visible only while the OLED is awake.
